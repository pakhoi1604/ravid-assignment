# Red-Team Failure-Mode Plan Review

## Scope

- Reviewed `plan.md` and all seven phase files in their current working-tree state.
- Verification role: Flow Tracer. Traced upload -> outbox -> worker -> generation -> retrieval -> RAG/quota, plus Compose outage and observability paths.
- Review only: no lint, build, or tests were run, as requested.

## Findings

### Critical

1. **The deterministic full-HTTP RAG E2E has no executable provider seam.** Phase 6 requires a deterministic provider by default and says it is attached only to `web` (`phase-06...md:24-33`), while the parent plan forbids implementing application features (`plan.md:19-22`). The actual HTTP entry point unconditionally constructs `RagService()` (`apps/rag/views.py:37-49`); that service defaults to `build_openrouter_chat_model` (`apps/rag/services.py:40-56`) and validates OpenRouter before retrieval (`apps/rag/services.py:241-244`). Compose exposes only OpenRouter settings to `web` (`compose.yaml:25-29`). Therefore `E2E-05` cannot be both real HTTP and deterministic/offline without adding an application-level provider-selection seam or substituting a fake OpenRouter-compatible network service. The plan names neither design, trust boundary, nor files needed. **Required correction:** choose and specify a concrete HTTP-compatible fake-provider topology, or explicitly authorize narrowly scoped application wiring and test its production fail-closed default.

2. **`E2E-10` promises recovery from a Chroma write outage, but the state machine makes that outage terminal.** The plan expects “Chroma down at write/retrieve ... recoverable” (`phase-06...md:73`) and globally requires dependency restoration without lost intent (`phase-06...md:100-103`). Flow: worker claims `PENDING -> PROCESSING` (`apps/documents/tasks.py:32-69`) -> vector write raises -> the task catches every exception and calls `_finalize_failure` (`apps/documents/tasks.py:206-214`) -> the job becomes `FAILURE` (`apps/documents/tasks.py:130-168`). Recovery selects only stale `PENDING` or `PROCESSING` jobs (`apps/documents/recovery.py:15-27`), never `FAILURE`. Restoring Chroma cannot resume that upload. Retrieval outage is retryable by a later chat request; write outage is not. **Required correction:** split write and retrieval scenarios with different oracles, record write outage as terminal/manual re-upload under the current contract, or explicitly scope a retry transition as a product change.

### High

3. **The killed-worker E2E has no bounded route to the recovery branch.** `E2E-08` expects a killed `PROCESSING` worker to recover within the suite (`phase-06...md:71,82-86`), but production recovery requires `lease_expires_at <= now` (`apps/documents/recovery.py:23-26`). The default processing lease is 2,100 seconds (`config/settings/base.py:180-185`; `compose.yaml:53,135`), recovery runs every 60 seconds (`config/settings/base.py:137-140`), and configuration rejects a stale threshold shorter than Celery's hard limit plus safety (`config/settings/base.py:232-233`). The plan neither budgets a 35+ minute case nor specifies a test profile that consistently lowers `CELERY_TASK_TIME_LIMIT`, lease safety, stale threshold, and Beat cadence across `web`, `celery`, and `beat`. **Required correction:** define an isolated recovery configuration with internally valid short timings, exact upper deadline, and an oracle proving the job entered `PROCESSING` before kill.

4. **Max-attempt recovery can strand partial vectors forever, and the plan's separated scenarios miss the leak.** `DUR-11` checks only “no redispatch; manual intervention code,” while `DUR-12` cleans only already-`STALE` generations (`phase-03...md:74-75`). On a max-attempt `PROCESSING` job, recovery writes job `FAILURE` and returns without marking its current generation stale (`apps/documents/recovery.py:29-36`). Cleanup selects only manifests with `status=STALE` (`apps/documents/recovery.py:98-114`). Any partial generation left `WRITING` after a killed worker is invisible but permanently ineligible for cleanup. This violates the phase's safe-cleanup claim and “each crash ... recoverable/auditable” success criterion (`phase-03...md:24-27,96-101`). **Required correction:** add a combined max-attempt-after-partial-write scenario with DB manifest and raw Chroma oracles, then either require a remediation transition or document the permanent storage leak as a residual risk with an operator procedure.

5. **The load oracle requires queue backpressure that the product explicitly does not have.** `PERF-02` requires concurrent uploads to leave a “bounded queue” (`phase-07...md:73-75`), and `SEC-05` assumes rapid upload/query/poll abuse remains bounded (`phase-07...md:69-70`). Upload commits durable dispatch intent for every accepted request (`apps/documents/views.py:42-60`); the publisher drains only a configurable batch (`apps/documents/dispatch.py:67-107`), and the architecture explicitly says embedding/provider work has no workload-specific concurrency or backpressure controls (`docs/system-architecture.md:171-176`). A finite benchmark can observe growth, but it cannot prove a bound that is not enforced. **Required correction:** replace “bounded queue” with measurable saturation/backlog/recovery budgets and an accepted maximum test load, or scope an actual admission/backpressure feature rather than pretending a test supplies it.

6. **The observability acceptance criteria are not supported by any emitted event model.** Phase 7 requires reconstructing success/failure/retry/recovery using safe IDs, codes, and timestamps, plus stage durations (`phase-07...md:23-35,77-89`), but its file map only reads settings and creates tests/reporting (`phase-07...md:37-46`). `LOGGING` merely selects a JSON formatter (`config/settings/base.py:235-253`). Dispatch emits no events (`apps/documents/dispatch.py:38-131`); successful claim, activation, recovery, and cleanup paths emit none (`apps/documents/tasks.py:32-168`; `apps/documents/recovery.py:15-150`). Existing logs cover invalid tasks, unexpected ingestion exceptions, and a few RAG/accounting warnings (`apps/documents/tasks.py:44-46,194-213`; `apps/rag/services.py:102-121`). Tests cannot assert correlations or stage timing that are never emitted. **Required correction:** define a minimal event schema and explicitly authorize instrumentation files, or reduce the oracle to the sparse events actually present and stop claiming transition reconstruction.

### Medium

7. **`SEC-02` has a disjunctive oracle that can pass the unsafe branch.** It combines forged vector metadata and prompt-injection content, then accepts “rejected **or** treated as data” (`phase-07...md:67`). Those inputs cross different boundaries: forged owner/document/generation metadata must fail closed before leaving retrieval (`apps/documents/vector_store.py:273-309`; `apps/documents/retrieval.py:54-60`), while a valid owner chunk containing hostile text may reach the prompt as untrusted evidence (`apps/rag/prompts.py:35-38`). A single `or` assertion can accept forged metadata being forwarded as prompt data. **Required correction:** split this into two scenario IDs with mandatory, mutually exclusive oracles: metadata rejection with zero provider call, and valid-owner prompt-injection content framed as data with a bounded provider response.

8. **Compose isolation is asserted but not made executable against the current fixed host bindings.** Phase 6 says every run receives unique Compose project, volumes, and ports (`phase-06...md:29-33`), but current Compose binds fixed `127.0.0.1:8000` and `127.0.0.1:5555` (`compose.yaml:64-65,245-246`). Its implementation steps mention only project/volume cleanup, not the required port override (`phase-06...md:80-87`), and its final diagnostic command is an unscoped `docker compose ps` (`phase-06...md:91-96`). A unique project name does not prevent host-port collisions or ensure diagnostics target that project. **Required correction:** specify the override mechanism and environment variables for both ports, propagate the resolved base URL to the driver, and require every Compose command (including diagnostics and teardown) to use the validated project/override arguments.

## Plan Status Recommendation

Phase 1-7 remain `Pending`. Do not begin implementation until Critical findings 1-2 and High findings 3-6 are resolved in the plan. Findings 7-8 must be corrected before their respective security and Compose lanes are treated as gates.

Status: BLOCKED

Summary: Eight production-relevant plan flaws found: 2 Critical, 4 High, 2 Medium. The largest blockers are an absent deterministic HTTP provider seam and a false claim that Chroma write failures recover under the current ingestion state machine.

Concerns: The plan repeatedly assigns tests oracles for behavior the application does not implement (recovery, backpressure, correlated events). Without explicit scope decisions, implementation will either introduce hidden product changes or weaken assertions until the suite passes without proving the stated invariants.
