# Phase 1: Scaffold Django Application

## Overview

Create the Python dependency definition, Django project, app boundaries, settings profiles, root URL
configuration, and liveness/OpenAPI surface. Keep business apps empty of invented feature behavior.

## Context Links

- [Plan overview](./plan.md)
- [Assignment](../../2026-08-30%20R.A.V.I.D.md)

## Requirements

- Functional: Django starts with `config.settings.local`; test and production settings import a
  shared base.
- Functional: `/api/health/` returns a small public JSON liveness response.
- Functional: drf-spectacular exposes `/api/schema/` and `/api/docs/`.
- Functional: Django discovers `accounts`, `common`, `documents`, and `rag` under `apps/`.
- Non-functional: Python 3.12 dependency resolution is captured in `uv.lock`.
- Non-functional: settings read secrets and deployment values from environment variables.
- Non-functional: no upload, ingestion, query, billing, or HyDE behavior is added.

## Architecture

```text
manage.py -> config/settings/{base,local,test,production}.py
          -> config/urls.py
             -> apps/common/urls.py -> health view

apps/
  accounts/   future identity, subscription, and daily usage ownership
  documents/  future documents and ingestion jobs
  rag/        future LangChain retrieval, OpenRouter, and HyDE
  common/     shared health and narrowly reusable infrastructure
```

Use Django's built-in user model for the foundation. A custom user adds migration and authentication
policy without being required for `user_id` ownership.

## Dependency Groups

- Core runtime: Django, Django REST Framework, drf-spectacular, SimpleJWT, Celery Redis support,
  psycopg, Flower, Gunicorn, and structured JSON logging.
- RAG extra: LangChain core integrations, `langchain-chroma`, `langchain-huggingface`,
  `langchain-openai`, Chroma client, sentence-transformers, and pypdf.
- Development: pytest, pytest-django, pytest-cov, Ruff, Bandit, and pip-audit.
- Pin the resolved set in `uv.lock`; do not rely on unconstrained latest packages in Docker.

## Implementation Steps

1. Initialize `pyproject.toml` for Python 3.12 with core, RAG, and development dependency groups.
2. Configure Ruff, pytest-django, coverage source paths, and package discovery in `pyproject.toml`.
3. Generate and commit `uv.lock`; verify a clean `uv sync --all-extras --dev --frozen`.
4. Create Django project entrypoints and split settings into base/local/test/production modules.
5. Keep base settings environment-driven; production must require a real `SECRET_KEY` and
   PostgreSQL configuration, while test settings may use isolated SQLite and eager Celery.
6. Create the four app packages and register their `AppConfig` classes.
7. Add public health, OpenAPI schema, and Swagger routes only.
8. Generate baseline Django migrations only when Django reports them; do not create feature models.
9. Run `uv run python manage.py check` under local and test settings.

## Security Considerations

- Never put usable credentials or API keys in source-controlled settings.
- Default permissions should be authenticated for future DRF endpoints; explicitly mark only health
  and API documentation as public.
- Keep `DEBUG` disabled in production and parse `ALLOWED_HOSTS` from environment.
- Do not log environment values or future private document content.

## Risk Assessment

- LangChain and Chroma packages change quickly. Mitigation: lock the complete compatible set and
  verify imports during this phase.
- Split settings can drift. Mitigation: keep base authoritative and override only database, debug,
  Celery eager mode, and external-client stubs where needed.
- Empty app files can become speculative abstraction. Mitigation: create only Django app boundaries;
  add serializers, services, tasks, and URLs with the feature that owns them.
