# Phase 4: Verify New Session Behavior

## Overview

Prove that the repaired `.codex` configuration is loaded automatically by new Codex sessions and that no hook is merely present on disk.

## Requirements

- Functional: validate JSON, command existence, manual hook execution, and runtime hook firing.
- Functional: verify fresh-session behavior, not only current-session manual calls.
- Non-functional: avoid destructive test commands and avoid reading real secrets.

## Architecture

Verification must cover two layers:

1. Static registry correctness: JSON shape, path existence, script execution.
2. Runtime activation: a new Codex session fires the configured events without manual script invocation.

## Related Code Files

- Read: `.codex/hooks.json`
- Read: `.codex/config.toml`
- Read: `.codex/hooks/*.cjs`
- Modify only if needed: docs or plan status after verification

## Implementation Steps

1. Run JSON validation against `.codex/hooks.json`.
2. For each registered command, verify the script file exists and `node <script>` handles empty/minimal stdin safely.
3. Test `UserPromptSubmit` with a prompt payload that should trigger or pass `simplify-gate`.
4. Test `PreToolUse` with harmless payloads:
   - `Write` payload for `descriptive-name`
   - sensitive path payload for `privacy-block`
   - blocked ignored directory payload for `scout-block`
5. Start or request a fresh Codex session and check which hooks fire automatically.
6. For notification/subagent events, run a deliberate attention-needed scenario and confirm notification/context injection behavior if supported.
7. Update this plan with final supported/unsupported event matrix.

## Success Criteria

- [x] Static validation passes.
- [x] Manual payload tests pass for every registered script.
- [x] A new Codex session loads `.codex/hooks.json` without user-specified manual setup.
- [x] Restored baseline safety-blocking hooks fire automatically in realistic Codex actions.
- [x] Newly added hooks either fire automatically or are explicitly marked unsupported with the reason.
- [x] Final implementation handoff includes exact verified commands and remaining limitations.

## Verification Notes

- Static checks passed: JSON parse, command existence, `node --check`, and `git diff --check`.
- Manual payload checks passed outside the tool sandbox for generated wrappers. Inside the sandbox, nested `spawnSync` returns `EPERM`; this is a tool-execution sandbox limitation, not a hook output failure.
- Initial fresh-session check exposed two runtime issues: `codex exec --json` did not fire project `PreToolUse`, and the interactive runtime rejected old `permissionDecision: "deny"` wrapper output as invalid pre-tool-use JSON.
- Codex wrappers now emit `decision: "block"` for blocking `PreToolUse` results; `descriptive-name` emits Codex `additional_context` for allow/context behavior.
- Fresh interactive activation passed with Codex CLI v0.151.0: the project hook registry loaded, Codex prompted for changed-hook trust, and `PreToolUse` blocked a shell command before command execution when it targeted an ignored dependency path.
- `UserPromptSubmit` is registered and manually verified, but fresh-session blocking was not proven because this checkout does not enable the simplify gate threshold in `.ck.json` or `.codex/.ck.json`.
- Hash-named wrappers were generated by `ck migrate`, then manually patched for Codex CLI v0.151.0 output schema. Do not regenerate them until the migration template emits `decision: "block"` for `PreToolUse` blocks and `additional_context` for context injection.
- Remaining limitation: non-interactive `codex exec --json` did not fire the project `PreToolUse` hook in the same ignored-path scenario, even with `--dangerously-bypass-hook-trust`.
